# 架构设计工作区

[English](spec-governance--architecture-design.md) | 中文

## 实现什么

架构设计工作区会把产品功能图与软件架构模型分开。它记录稳定的组件、包含关系、类型化依赖、部署单元、源码所有权，以及 Feature 与组件之间的多对多映射。专用架构助手根据这些仓库事实讨论待规划能力应该放在哪里，而不会把 Feature 父级、源码目录或插件边界当成同一个决定。

## 最终效果

开发者提出一项能力后，Blueprint 会给出产品位置和组件位置的备选方案，在变更前后架构图中突出推荐的节点与类型化边，并列出接口、部署、文件所有权、兼容性和迁移影响。架构助手的完整消息历史、流式回答和工具活动始终内嵌在“架构设计”工作区。它的独立后台 Session 会被立即归档，在保留持久恢复能力的同时，不出现在普通 Workspace 或 Ungrouped 聊天分组中；已有的未归档架构 Session 会在重新打开时自动迁移。Feature 和组件的身份不会因为父级或容器变化而改变，因此一次架构讨论不会自动重命名文档、后代节点或审批身份。开发者可以决定扩展现有组件、新增内部组件、新增平级服务，或者引入可独立安装的插件。

## 怎么使用

打开“架构设计”，选择现有 Feature 或描述一项待规划能力，然后让架构助手评估位置。检查建议的 Feature 关系、组件分配、依赖、部署边界、受影响路径、备选方案和仍未解决的产品决策。比较当前图与提议图，再明确接受架构提案，之后 Blueprint 才会同步已登记的架构记录和 proposed Spec。开始实现前，仍需通过现有的精确哈希工作流审核并批准最终 Spec。

## 注意事项

Feature 的 `Parent` 只表示产品能力包含关系；调用、复用、集成和共享页面使用类型化架构关系。源码文件按照组件所有权组织，而不是照搬 Feature 树；网页只有具备独立安装、版本、权限或宿主扩展生命周期时才需要成为新插件。架构助手以当前 Feature 目录、组件模型、权威文档、清单和已批准决策为依据，区分仓库事实与假设，不能自行批准提案，也不能在规划阶段修改实现文件。
