# 架构设计工作区

[English](spec-governance--architecture-design.md) | 中文

## 实现什么

架构设计工作区会把产品功能图与软件架构模型分开。它记录稳定的组件、包含关系、类型化依赖、部署单元、源码所有权，以及 Feature 与组件之间的多对多映射。专用架构助手根据这些仓库事实讨论待规划能力应该放在哪里，而不会把 Feature 父级、源码目录或插件边界当成同一个决定。

## 最终效果

开发者提出一项能力后，Blueprint 会给出产品位置和组件位置的备选方案，并列出接口、部署、文件所有权、兼容性和迁移影响。架构助手的完整消息历史、流式回答和工具活动始终内嵌在“架构设计”工作区。它的独立后台 Session 会被立即归档，在保留持久恢复能力的同时，不出现在普通 Workspace 或 Ungrouped 聊天分组中；已有的未归档架构 Session 会在重新打开时自动迁移。当建议能够精确表达为一个受支持的组件变更时，回答会包含内嵌提案卡片，由 Host 计算预览，并提供一个独立的开发者确认应用操作。Feature 和组件的身份不会因为父级或容器变化而改变，因此一次架构讨论不会自动重命名文档、后代节点或审批身份。

## 怎么使用

打开“架构设计”。如果逻辑组件图为空，点击**初始化架构模型**，检查根据项目清单推导出的仓库级组件 ID、类型和拥有路径，再确认创建。随后选择现有 Feature 或描述一项待规划能力，让架构助手评估位置并细化这个粗粒度初始边界。检查建议的产品关系、组件分配、依赖、部署边界、受影响路径、备选方案和仍未解决的决定。对于受支持的单组件提案，先点击**生成变更预览**并检查 Host 返回的精确差异，再点击**确认并应用**。Blueprint 会应用该预览哈希并刷新架构图。如果实现或 Feature 规划文档也需要变化，开发前仍需使用其独立的 Spec 工作流。

## 注意事项

Feature 的 `Parent` 只表示产品能力包含关系；调用、复用、集成和共享页面可能属于架构关系，但当前提案卡片只应用已经登记的 Component 对 Component 关系类型。它不提供 Component Tab、通用 Relationships 面板、Feature 层级编辑、Feature 对 Feature 关系写入、结构化契约元数据或多组件事务。源码文件按照组件所有权组织，而不是照搬 Feature 树；网页只有具备独立安装、版本、权限或宿主扩展生命周期时才需要成为新插件。架构助手以当前 Feature 目录、组件模型、权威文档、清单和已批准决策为依据，区分仓库事实与假设，不能自行应用或批准提案。
