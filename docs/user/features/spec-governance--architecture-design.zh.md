# DSH 原生规格驱动 Blueprint

[English](spec-governance--architecture-design.md) | 中文

## 实现什么

Design Blueprint 是一个 DSH 插件，它把开发者的一条需求转换成经过完善的规格、实现、验证证据和更新后的系统地图。开发者只在 DSH 普通 Chat 中工作，不需要选择 Spec 助手、架构助手、实现者、验收者、生命周期阶段或仓库文件。

Blueprint 在一条有明确取舍的工作流中结合三种思路：

- 借鉴 Spec Kit 的完善过程，发现歧义、拆解用户场景、检查需求质量，并在实现前分析一致性。
- 借鉴 OpenSpec 的变更增量，用增量描述正在改变什么；完成的变更合并后，Feature brief 继续作为当前行为事实。
- 使用 Blueprint 的 Feature 树把当前系统展示成可浏览的层级；每个节点可以查看行为、代码归属、依赖、测试、活动变更和历史决策。

默认路径刻意保持简短。开发者描述需求后，Blueprint 定位拥有该需求的 Feature，读取已有 brief、代码、测试和相关权威文档，形成变更草案，只追问会实质改变行为的问题，实现已经接受的结果，完成验证，再更新 Feature 当前事实。高级工件和诊断细节仍然可以查看，但不成为必经的用户工作流。

## 规格完善

Blueprint 必须完善需求，而不是把原话复制进 Markdown。对于每项有实质意义的变更，它会识别参与者与目标、入口、正常流程、输入与输出、状态变化、业务规则、失败、边界情况、兼容约束、非目标和可观察的验收场景。

存在实质歧义时，系统在一轮中最多提出三个聚焦问题。不会实质改变结果的缺口会变成可见假设，并且可以在实现之前或实现期间修正。需求使用稳定标识和具体场景，使每项实现任务和验证结果都能追溯到预期行为。

实现前，Blueprint 在内部完成三层质量检查：

1. 澄清检查寻找缺失决策和彼此冲突的解释。
2. 需求清单检查规格是否完整、明确、有边界并且可以验证。
3. 跨工件分析检查需求增量、可选技术设计、任务、代码范围和验证计划是否一致。

简单变更可以只使用一份紧凑的变更文档。只有工作改变模块归属、公共契约、持久化、部署、权限、迁移或其他结构边界时，才生成技术设计。开发者可以查看并编辑全部工件，但不需要手工推动每个阶段。

## 当前事实与变更历史

Feature 地图及其双语 Feature brief 描述系统现在能做什么。活动变更只描述正在考虑或实现的增量。变更完成后会更新拥有它的 Feature 当前 brief，并把不可变的变更包移入历史。被拒绝或放弃的变更永远不会成为当前事实。

每项活动变更保留原始需求、完善后的要求与场景、明确假设、可选设计、有序任务、实现进度和验证证据。这样既能理解当前系统，也不会丢失行为发生变化的原因。

Feature 树是主要产品层级。父子关系表达能力包含；依赖和技术归属作为独立详情存在，不再形成一套需要开发者维护的第二层级。点击 Feature 后可以查看摘要、当前行为、子功能、依赖、主要代码路径、测试、文档、活动变更和已完成变更历史。

## DSH 插件契约

DSH 普通 Chat 是唯一对话界面。Blueprint 提供一个带前导输入的 `/blueprint ` 命令和等价的模型工具；普通自然语言也可以进入同一种请求契约。`/blueprint-status` 和 `/blueprint-map` 是确定性快捷命令。Blueprint Web 只是仪表盘和文档查看器，不是另一个 Chat。

实现必须面向从活动 profile 解析出的一个精确 DSH 版本。Host 命令、模型工具、服务、Agent 或 Workflow 延续、类型化 Host API、Client slot 和清理只能使用该版本正式记录的公开扩展点。插件不能修改 DSH 核心、调用私有输入框 API、根据 Session 标题或 Prompt 标记推断权限，也不能把当前 master 手册中的 API 与较旧的已安装包混用。

插件继续作为普通可安装 DSH bundle。Host 与 Client 职责保持分离，每项注册都随其 Cordis 作用域可靠释放，兼容测试会启动真实目标 profile。仓库工件是持久权威；浏览器存储、React effect、进程内 Job 和助手正文都不是权威。

## 开发者体验

日常交互是：开发者需求 → 完善规格 → 只追问阻塞问题 → 实现 → 验证 → 更新 Feature 地图和当前 brief。

用户可见进度只保留 `refining`、`ready`、`implementing`、`verifying`、`blocked` 和 `completed`。内部 DSH 回合、工具调用、快照、重试和诊断记录可以存在，但只在需要解释失败时展示。

完成条件是已声明测试与仓库检查通过，并且 Feature 当前事实与已经交付的行为一致。高风险变更可以要求显式审核或独立验收；普通有界变更不会强制创建多 Agent 仪式。
